# Ranked-original prefix: frozen offline preflight and next screen

This is a **candidate-delivery** result, not answer quality. It uses the exact 14 already exposed LongMemEval-S development IDs from `eval/longmemeval/pilot.json` and the pinned cleaned-S source SHA-256 `d6f21ea9d60a0d56f34a05b609c79c88a451d2ae03597821ea3d5a9678c3a442`. Each original Markdown history was rendered temporarily; the actual `recall-managed --agent --auto --offset 0` CLI returned the first ranked page. The experiment selected the longest ranked prefix whose full original bodies total at most 150,000 UTF-8 bytes. This is a **byte-bound first transport**, not a top-k or permanent source limit. The private manifest with exact paths and per-case counts is `/private/tmp/graphmory-ranked-prefix-preflight-v1.json` (SHA-256 `a8049ed3583469775a9dea084297ab789c8d2002fab2475293c141e213667e78`). Temporary renderings were removed.

Across the 12 answerable cases, the selected first-page originals contain at least one note from **every annotated evidence group in 12/12 cases**. The two official abstention cases are excluded from that denominator. Prefixes contain 10–13 notes across all 14 cases; source bytes range from 112,929 to 149,688. Both multi-session aggregation cases contain all annotated groups in their first transport: `gpt4_d84a3211` uses 12 notes / 140,419 bytes (4/4 groups), and `67e0d0f2` uses 10 notes / 135,831 bytes (2/2 groups). Every first CLI page still reports `hasMore=true`, so the Curator must retain continuation and source-index access. Annotated paths are opportunities for evidence, not independently verified complete answer labels; alternative supporting paths and semantics remain possible.

The current `--prefetch-wide-originals` mode returned **zero originals** for those two multi-session cases: it skipped the 31-path page as `more-candidates` and the 10-path page as `focused-query`. A full-history collector instead had to map four pages and roughly 0.55 MB of prompt bytes per case, failing the two-call cap. These observations support testing a query-directed first transport; they do not prove that a model will use the evidence correctly.

## Frozen next development screen, before treatment answers

Implement one opt-in `--ranked-originals` mode in the existing Curator runner. It reads the longest ranked first-page prefix within half of the common 300,000-byte prompt ceiling, validates original SHA-256s, and supplies those originals with the current retrieval page. Preserve all candidate paths, pagination and the common `--source-index` allowlist. If a first note does not fit, report no prefetch; never silently truncate an original. Keep the ordinary control and native Basic Memory hybrid search unchanged. All arms use the same original-reader CLI when `--source-index` is enabled, the same Curator/Lead models, `--max-rounds 3`, answer schema and hard prompt ceiling.

Screen the two already exposed, provisionally source-supported multi-session cases `gpt4_d84a3211` and `67e0d0f2` in three paired arms: current Graphmory, Graphmory ranked-original transport and native Basic Memory hybrid. Run one generation per case/arm with rotated arm order and fresh contexts: **six planned workflows**, no replacements after observing answers. Build and verify Basic's native index for each case. Freeze reader inputs, source hashes, executable/model identities, code hashes, command flags and arm order in a new manifest before any model call. Record every attempted/failed slot.

Judge supported-complete answers and original-path citations against source-bound facts, with official answers/scores kept separate. Preserve unresolved judgments; the failed RAGTruth judge cannot decide a winner. Secondary metrics are whole-workflow wall time, gross/cached input and output tokens, tool bytes, calls, original-read and Basic ingestion time. This two-case screen can reject a mechanism on an observed answer loss, missing original, citation error or resource regression. It **cannot** justify a general superiority or default change. Any promising result requires independently adjudicated labels and a separately preregistered source-disjoint holdout. Do not tune the byte budget, selected IDs or prompts in response to these six outputs.

## Post-implementation transport verification, still before model answers

The opt-in mode was then wired into the existing runner. A temporary fake Codex host returned schema-valid fixture messages; it did not judge or answer either memory question. Against the actual two prepared LongMemEval histories, both runs completed their transport and runner contract: `gpt4_d84a3211` supplied 12 originals / 140,419 source bytes in a 183,304-byte first Curator prompt; `67e0d0f2` supplied 10 originals / 135,831 source bytes in a 158,416-byte first Curator prompt. Each required two fake-host calls (Curator and Lead), within the unchanged 300,000-byte per-prompt ceiling. Actual model tokens, answer correctness, citation support and latency remain unmeasured. The temporary host and trial outputs were removed.

Native Basic Memory 0.23.2 indices were built separately from the same two original corpora. Its local BGE-small-en-v1.5 embedding index reported 48/48 and 52/52 notes embedded, zero skips/errors, with build times of 33.751 and 43.809 seconds. Basic normalized all indexed Markdown bodies, so the matched `--source-index` workflow reads the same verified originals as the Graphmory arms while retaining Basic's native hybrid search. An offline native-search smoke with the per-index cached model returned ten results per case in 2.525 and 1.929 process-wall seconds and about 70/69 KB of stdout. These two isolated smoke times are **not** paired workflow latency results; index build cost is separate and must be reported alongside any later query timings.
