# Architecture decision: paginated evidence collection with a source ledger

Status: design decision only; no implementation, model calls, or benchmark run authorized by this memo itself. Existing defaults and official scores remain unchanged.

## Decision and evidence

Choose **one architecture change: a Curator collection phase that consumes paginated original Markdown into a provenance-preserving evidence ledger before producing its answer summary**. Retrieval ranks the reading order; top-3/top-10 are page diagnostics, never completeness criteria. A page size is a transport bound, not a limit on related evidence.

The strongest observed failure is incomplete evidence use and aggregation. In the [live three-arm diagnostic](../evaluation/prefetch-three-arm-2026-09-28.md), normal Graphmory read only one of two annotated paths on the beach and pets questions, while full-source delivery exposed both. The [compact experiment](../evaluation/prefetch-compact-live-ab-2026-09-28.md) additionally exposed an exhaustive-count label failure: relevant events existed elsewhere in the full history. Neither small diagnostic proves a general gain, but both motivate collecting and accounting for evidence before synthesis. The full 14-case retrieval diagnostic already found all annotated evidence by @10, so better early ranking alone does not establish that the Curator will read, reconcile, and cite all necessary notes.

Research basis: the map/reduce aggregation pattern in [Edge et al., GraphRAG](https://arxiv.org/abs/2404.16130), as documented in the [verified source note](next-architecture-evidence-2026-09-28.md), motivates mapping over source batches and reducing source-bearing records. This is an adaptation, not a replication of GraphRAG: do not add entity extraction, community graphs, or generated index summaries. The paper's global-sensemaking results do not prove exact-count correctness or cost benefits here.

Reject contextual prefixes as the next priority. `splitMarkdownSections` in `src/retrieval.mjs` already includes document path, title, metadata, and heading ancestry in the section representation and BM25F fields. Generated context would be genuinely additional, but the proposed static prefix mostly duplicates existing context. The source note's @3 acceptance bar also conflicts with the user's requirement to gather related Markdown through pagination. Revisit representation changes only if complete collection still misses discoverable relevant sources.

## Collection contract and code touchpoints

1. Add an opt-in collection state machine around the existing Curator tool loop: collect, reconcile, then summarize. Track source path/hash, original line span, quoted support, candidate fact/event, and unresolved ambiguity. A fact becomes usable only after its quote/span is checked against the original; synthesis cites originals, not ledger prose. Retain conflicting facts and event identity uncertainty rather than silently merging them.
2. In `src/memory-recall.mjs`, expose whether the candidate pool is truncated by `perMethodLimit`, file enumeration, or lifecycle/scope filters. `hasMore: false` currently means the fused, per-lane-limited pool ended; it must not imply all related notes were found. In collection mode, pagination must eventually reach the whole eligible pool for the declared query/scope. Keep deterministic ordering and detect changed source hashes across pages.
3. Integrate this contract through `src/decision-recall.mjs` and the Curator runner used by `scripts/run-prefetch-three-arm.py`. Read every returned original completely, deduplicate by path/hash, and maintain the ledger across pages. A page ending cannot trigger a final summary while a continuation remains. Inspect the runner's actual helper ownership before editing; do not create a parallel orchestration stack.
4. For exhaustive count/aggregation questions on these history-scoped corpora, enumerate and scan every Markdown note in that history. This closes the observed keyword/annotation blind spot. For other questions, report completeness only relative to the declared scope and explored candidate pool. General semantic relevance cannot be certified by lexical exhaustion alone.
5. Resource exhaustion yields an explicit incomplete collection result with unread paths/pages and unresolved facts; it must never become an exhaustive answer. Use a bounded per-page payload with complete-note continuation for large notes. Evidence already read must remain addressable for final support checks.

This is one collect-and-reduce architecture, not a bundle of ranking, query-rewriting, embedding, and judge changes. Keep the existing retrieval scoring and answer models fixed. Original full texts may be streamed through batch mapping; ledger summaries must not replace source access when verifying a disputed event.

## Bounded development preregistration

Before implementation measurements, freeze one manifest with **eight exposed development questions**, source hashes, full-history source-checked labels, exact commands/models, and arm order. Include four multi-note aggregation/count questions, two specific-fact questions, and two unanswerable questions from exposed histories. Any unresolved label ambiguity blocks that slot before generation; do not silently substitute after seeing answers. Retain official references and raw official-function scores separately from the source-support rubric.

Run three paired arms on the same host and identical original corpus: current Graphmory Curator, Graphmory collection-ledger Curator, and native Basic Memory hybrid Curator. This is 24 planned answer workflows, one generation per slot, with rotated arm order and fresh model contexts. Use the same final-answer schema, model versions/reasoning, full-original read capability, scope access, and hard resource ceilings in every arm. Basic Memory must have usable continuation and original reads; inability to provide equivalent access invalidates the paired comparator rather than counting as its answer failure. Record indexed/original normalization separately.

Primary outcome: supported-complete final answers with original citations, counted per question. Apply the frozen source rubric blind to arm identity; any unresolved support judgment remains unresolved and cannot supply a win. Preserve all failed/invalid attempts. Do not launch another judge-calibration program: unresolved judgments prevent promotion.

Secondary outcomes: unsupported assertions, correct abstention, number of missed eligible originals for exhaustive questions, whole-workflow wall time including reads, gross/cached tokens, tool bytes, model/tool calls, and separately amortized ingestion/refresh work. Dollar cost is reported only where actual tariff/accounting supports it. Startup-only search timing is not workflow latency.

**Development continuation gate:** treatment must have no supported-complete loss against either comparator on any valid pair, improve at least two valid questions over current Graphmory, retain correct abstention on both unanswerable cases, and introduce zero unsupported cited claims. It must also remain within 1.5× current Graphmory aggregate gross input tokens and 1.5× median whole-workflow time on the matched valid slots. These are predeclared engineering screening caps, not paper-derived benefits or statistical noninferiority. Equal quality with no meaningful gain fails this architecture screen.

Stop after this single batch. Permit at most one revision for an objectively demonstrated implementation/protocol defect, recorded with a new manifest and all prior attempts retained; do not tune thresholds, cases, ledger prompts, or page sizes to answer losses. If the gate fails, keep the feature experimental and record rejection. A defect requiring a broader redesign ends this experiment.

## Holdout and dependencies

A development pass earns only a separately preregistered confirmatory run. Keep the independent source-disjoint holdout sealed throughout implementation and development. Its custodian must verify full-history labels before freezing it, hide questions/labels from the implementer, and freeze sample size, paired quality/noninferiority analysis, abstention/citation criteria, variance repetitions, and practical latency/cost gates before release. Use existing project acceptance gates where already declared; this memo neither weakens them nor claims that eight questions establish noninferiority. If no adequately powered, independently preserved holdout is ready, promotion is blocked while the opt-in implementation remains available for inspection.

Dependencies: inspect existing Curator runner ownership; verify comparator pagination/original-read access; freeze valid full-history development labels; establish actual resource ceilings from the existing runner; and ensure every attempt and source manifest is reproducible. Risks are omitted facts during ledger extraction, duplicate-event merging, excessive sequential map calls, prompt injection in source notes, stale page cursors, and false completeness from bounded scans. Original-span validation, explicit ambiguity, source hashes, and incomplete-state handling are required behavior, not optional follow-up optimizations.
