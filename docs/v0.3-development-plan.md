# v0.3 Development Plan

This branch starts the development version after the v0.2 first public push.

The goal is not to copy `claude-obsidian`. The goal is to understand its architecture, decide which problems it solves at a different layer, and improve Memory Patch Harness without losing its smaller contract-first shape.

## Architecture Studied: claude-obsidian

`claude-obsidian` is best understood as an Obsidian vault operating system for Claude Code. It ships a working vault, skills, commands, scripts, tests, transport detection, retrieval, concurrency controls, and methodology routing.

Its architecture has several layers:

```text
source files / raw inputs
  -> ingest skills
  -> wiki pages: sources, entities, concepts, sessions
  -> index + hot cache + log
  -> query/retrieve/lint/save/autoresearch skills
  -> optional Obsidian CLI / MCP / filesystem transport
```

Key architectural components:

| Component | Role in claude-obsidian | What it teaches us | v0.3 Status |
|---|---|---|---|
| Hot cache (`wiki/hot.md`) | Short recent-context startup surface | Repeated agent sessions need a small, refreshable context view separate from canonical notes | Implemented: `render-hot-context.mjs`, `docs/hot-context-demo.md` |
| Index (`wiki/index.md`) | Master navigation map | A human-readable source map is useful before deep retrieval | Implemented: `examples/demo-memory-workspace/source-map.md` |
| Log (`wiki/log.md`) | Chronological activity trail | Chronology is useful as evidence, but should not be the only memory layer | Not adopted (chronology as evidence only, not memory layer) |
| Ingest/query/save/lint skills | Separate operations over the vault | Split memory work by operation, not by one giant prompt | Implemented: `recall`, `lifecycle-audit`, `curation-recommend`, `curation-apply`, `lint` in `brain-sync.mjs` |
| Transport detection | Chooses Obsidian CLI, MCP, or filesystem | Tool choice should be detected and recorded rather than guessed every run | Implemented: `adapters/opencode/`, `adapters/generic-agent/` guidance |
| Hybrid retrieval | BM25 plus optional contextual prefix/rerank | Retrieval should be optional, measurable, and degrade gracefully | Implemented: BM25F default, optional `recall-semantic`, `recall-rerank`, `eval-rerank.mjs` |
| Methodology router | Generic, LYT, PARA, Zettelkasten filing modes | Organization should be configurable and not hardcoded | Implemented: `examples/methodology-templates/` (generic default, PARA/LYT/Zettelkasten optional) |
| Multi-writer lock | Prevents parallel write corruption | If multiple agents can write, locking or single-writer discipline is necessary | Not implemented (no automated apply-to-vault path yet) |
| Lint skill | Finds orphans, dead links, gaps, stale claims | Memory needs maintenance, not only writes | Implemented: `brain-sync.mjs lint`, `health`, `lifecycle-audit`, `curation-recommend` |
| Audit docs/tests | Records architectural claims and failure fixes | Public claims need repeatable tests and visible audit history | Continuous: deterministic evals + release gate |

## Difference From Memory Patch Harness

Memory Patch Harness is intentionally smaller.

```text
verified task evidence
  -> lead agent writes Memory Patch
  -> Memory Curator validates/routes/links
  -> canonical Markdown memory
  -> Brain Brief recall
  -> optional Derived Index / Hot Context Pack
```

The key distinction:

- `claude-obsidian` is a full vault runtime.
- `memory-patch-harness` is a portable memory contract and eval harness that can sit inside many agent/vault systems.

## Architecture Lessons To Adopt

### 1. Hot context should be generated, not hand-maintained

Our `Hot Context Pack` matches the same need as `wiki/hot.md`, but ours should stay contract-based and generated from canonical notes.

v0.3 implementation:

- `hot-context-pack` is derived (not canonical) — schema at `schemas/hot-context-pack.schema.json`;
- `scripts/render-hot-context.mjs` renders it into Markdown;
- `docs/hot-context-demo.md` documents invalidation triggers;
- rendered example at `examples/hot-context-rendered.md`.

### 2. Memory needs a map before retrieval gets fancy

`claude-obsidian` relies on `index.md` before deeper reads. This supports our `Derived Index` direction.

v0.3 implementation:

- `examples/demo-memory-workspace/source-map.md` — tiny demo workspace with source map;
- derived indexes remain generic (filesystem, BM25, or manual maps);
- vector DB is opt-in only (`@huggingface/transformers` optional dependency);
- `brain-sync.mjs` `recall`, `recall-loop`, `recall-semantic` all accept `--scope` for project/domain filtering.

### 3. Tool/transport choice should be explicit

`claude-obsidian` records transport state in `.vault-meta/transport.json`.

v0.3 implementation:

- Adapter guidance published at `adapters/opencode/README.md` and `adapters/generic-agent/README.md` + `INSTALL.md`;
- Each adapter records memory access method (filesystem, MCP, Obsidian REST, Obsidian CLI, or custom);
- Core scripts remain filesystem-only.

### 4. Methodology support should be optional

PARA, LYT, and Zettelkasten are useful, but forcing one would make this harness too opinionated.

v0.3 implementation:

- Generic is the default (no forced methodology routing);
- `examples/methodology-templates/` provides optional PARA, LYT, and Zettelkasten READMEs with note-layout examples;
- Memory Curator reports existing vault conventions and follows them rather than enforcing a router.

### 5. Write safety matters only when writes become automated

`claude-obsidian` needs locks because parallel agents write vault pages.

v0.3 status:

- Harness remains read/validate/eval focused;
- `curation-apply` and `conflict-apply` commands exist but operate on structured plan files, not raw vault mutations;
- Write lock helper not implemented — still deferred until an automated apply-to-vault path is added.

### 6. Lint is the missing maintenance lane

The most useful architectural idea to borrow is not a feature, but a maintenance loop.

v0.3 implementation:

- `brain-sync.mjs lint --vault <path>` — general memory lint command;
- `brain-sync.mjs health --vault <path> --json` — deterministic health check covering unresolved links, duplicate titles, orphan notes, missing provenance/lifecycle markers, stale memory without revalidation, inbox backlog, raw captures outside Inbox, and secret-like values;
- `brain-sync.mjs lifecycle-audit --vault <path> --json` — stale-memory audit for expired `valid_until`, due `revalidate_when`, obsolete notes without replacement markers, active notes with stale language, raw memory outside Inbox, and tension notes without a decision path;
- `brain-sync.mjs curation-recommend --report <file> --queries <file>` — classifies miss patterns and suggests alias/frontmatter, MOC link, scope, and grouped-gold review candidates;
- Eval fixtures: `npm run eval:lifecycle`, `npm run eval:conflict`.

### 7. Live evaluation matters more than more architecture

`claude-obsidian` documents benchmark/audit history. Our current public gap is live-model results.

v0.3 implementation:

- `eval/live-agent/incidents.json` — public anonymized incident set (20+ scenarios);
- `eval/live-agent/run-template.md` — structured worksheet for recording model/prompt/budget/tool-call data;
- `scripts/eval-live-agent-score.mjs` — weighted rubric scorer (action correctness, provenance, scope, lifecycle, fabrication avoidance, leakage prevention);
- `docs/live-model-eval.md` — documented evaluation procedure, output shapes, and scoring commands;

**Blocked (requires real live-model runs):** `docs/live-model-results.md` still shows TBD — no live-model benchmark has been published yet. Proxy evals validate the harness; real model comparison remains a future step.

## What We Should Not Adopt Yet

- Full Obsidian vault plugin scope.
- Bundled images, GIFs, or heavy demo media.
- Forced methodology routing.
- Default external API retrieval.
- Multi-writer lock without an automated writer.
- Large seed wiki that makes the harness look bigger than it is.

## Definition Of Done For v0.3

- `npm run check` passes.
- No private vault or transcript content is committed.
- Architecture docs clearly say this is a contract harness, not a full Obsidian runtime.
- Live-model benchmark status is honest.
- New features remain optional and contract-backed.
- License and attribution files remain accurate.
